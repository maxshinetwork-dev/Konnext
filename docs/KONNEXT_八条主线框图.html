KONNEXT · 业务流架构提案

八条主线：人定关口，Agent 跑腿，数据库裁决

六个部门 + 决策 + 监管，共八条主线。原本由人判断的节点仍然由人判断； 两个监管点之间由 Agent 接力，每个 Agent 只做一次单一输入输出。 关键约束：Agent 只能提议，不能裁决 —— 所有"能不能"的判断留在数据库的 279 条策略和门禁里。 把鼠标放在任何一个节点上，看它干什么、谁验它、动了哪些表。

① 每个 Agent 的输出，必须有一个不是 Agent 的检查者

门禁 / 断言 / CHECK 约束 / 人，四选一。没有检查者的 Agent 不许上线 —— 幻觉不是靠任务变小消除的，是靠验出来的。

② 一条链上「连续没有检查者的 Agent」不许超过 1 个

串 8 个可以，只要中间有验的。真正该管的不是 Agent 的数量， 是多大比例的输出是机器可验的。

③ Agent 里绝对不能重写业务规则

提示词里只要出现一句「SM3 完成后才能开 S2」，这条规则就有了第二个副本 —— 然后它会和数据库里那条慢慢漂移，而且漂移那天不会报错。

交接点 · 一等公民

按部门切八条流，交接就变成了「线与线之间的边」—— 而边最容易没人负责。 KONNEXT 至今踩过的真 bug 一个都不在部门内部，全在交接处。 所以交接点单独建模，不许掉进两条流的缝里。鼠标放上去，看它连的是哪两条线。

⑧ 监管流 横跨全部七条线 · 内核必须是确定性的
★ 为什么监管流的内核不能是 Agent：v0.38 的倒休门禁静默失效，是 SQL 断言抓出来的 —— 门禁自己查不出自己没生效。同理 Agent 也查不出 Agent 的错，它们共享同一种失效方式。 用 Agent 监管 Agent，等于让两个近视眼互相验光。Agent 在这一层只能做「把 INV-XXX 翻译成人话」。
