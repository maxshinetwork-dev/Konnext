## 零、先定一件事：架构长什么样

```
浏览器（React）
    │  只调 API，不知道数据库存在
    ▼
后端 API（Next.js API Routes）
    │  ★ 在这里 SET app.account_id ← 取自服务器验证过的会话
    │    前端请求里带的任何身份信息一律忽略
    ▼
Supabase（PostgreSQL）
    130 条 RLS 策略 · 57 条断言 · 全部业务门禁
```

**为什么必须有中间那层：** RLS 靠 `SET app.account_id = '某人'` 判断你是谁。前端直连的话，**这句话由浏览器说了算**——改一行 JS 就能声称是核心管理员，全部权限瞬间失效。你的 Demo README 自己写过：「前端的登录框拦不住任何人」。

**这层后端只做两件事：认证 + 转发。** 业务逻辑全在数据库里，不用重写一遍。

| 层 | 技术 | 理由 |
|---|---|---|
| 前端 | React + TypeScript + Vite | TS 类型可从数据库生成，改 DDL 前端立刻编译报错 |
| 后端 | **Next.js**（前后端同项目） | 一次部署，不用维护两套；API Routes 就够 |
| 数据库 | Supabase（PostgreSQL 15+） | ★必须 15+，`security_invoker` 视图选项要它 |
| 短信 | Twilio + **澳洲手机号** | 见第三节 |
| 地图 | Google Distance Matrix API | 见第四节 |

**绝对不能做的三件事**（写进开发规范）：
1. ❌ 前端直连 Supabase
2. ❌ Service Key 或数据库连接串下发到浏览器
3. ❌ 前端直接查基表（`material`/`project`/`payment_milestone`…）——基表没有列级遮罩，**只查视图**

## 三、Twilio 短信（★最要紧的外部依赖）

**为什么最要紧**：Google 挂了系统照样能用（手填、看不到路况）；**短信挂了账号系统直接瘫掉**——无密码登录完全靠它。

| # | 事项 | 谁做 | 验收标准 |
|---|---|---|---|
| 3.1 | 注册 Twilio，**升级为付费账号** | 你 | 试用账号不能用字母发送者、发不到澳洲 |
| 3.2 | ★**买一个澳洲手机号**（+61 4xx） | 你 | **不要用字母发送者 ID** |
| 3.3 | 开通入向短信 Webhook | 我写代码，你配 | 手机回 YES，服务器收到 |
| 3.4 | 地理权限里勾选澳洲 | 你 | 能发到 +614 号码 |
| 3.5 | 号码格式统一 E.164 | 我 | 库里存的都是 `+614xxxxxxxx`，不是 `04xx xxx xxx` |

### ★ 为什么必须买手机号，不能用「KONNEXT」这种字母发送者

**字母发送者 ID 只能单向发，收件人回不了。** 我们有两处必须收回复：

- 提货确认（回 YES → 出库单自动转"已接收"）
- ~~登录验证码~~（这个只需发送，字母发送者也行，但两套发送渠道更麻烦）

**另外一条新规**：2026 年 7 月 1 日起，发给澳洲收件人的 Sender ID 需经 ACMA 的 SMS Sender ID Register 批准，未登记的会被打上「Unverified」标签或被过滤。用手机号可以绕开这套登记。

### 三个用途与验收

| 用途 | 验收标准 |
|---|---|
| **登录验证码** | 手机收到 6 位码，10 分钟内有效，用过即失效；再用同一个码登录失败 |
| **提货清单 + 回 YES** | 出库后提货人收到中英对照清单；回 YES 后 `stock_out.status` 变 `received`、`received_via='sms_yes'` |
| **部门交接通知** | 售前点第六步签字 → 财务手机收到「请开 S1 定金 Invoice」 |

### 失败处理（现在就定，别等出事）

- 发送失败 → `notification.status='failed'`，**在待办中心红色列出**，人工跟进
- **绝不因为短信失败而回滚业务**——货已经出了就是出了，短信是通知不是门禁
- 入向 Webhook 要**幂等**：同一条回复重复推送不能重复置"已接收"

## 七、上线前最后一遍检查（Go / No-Go）

一条不过就不开门：

```sql
-- ① 断言必须全过
SELECT * FROM fn_assertion_summary();
-- 期望：✓ 全部通过

-- ② 视图必须全部 security_invoker（否则权限形同虚设）
SELECT count(*) FROM pg_class
 WHERE relkind='v' AND relnamespace='public'::regnamespace
   AND (reloptions IS NULL OR NOT ('security_invoker=true' = ANY(reloptions)));
-- 期望：0

-- ③ 关键表必须开 RLS
SELECT relname FROM pg_class WHERE relkind='r'
   AND relname IN ('project','payment_milestone','material','stock_out','daily_payroll','app_account')
   AND NOT relrowsecurity;
-- 期望：0 行

-- ④ 期初移库必须做完
SELECT count(*) FROM v_opening_status WHERE NOT opening_done;
-- 期望：0

-- ⑤ 管理员账号健康
SELECT * FROM v_admin_health;
-- 期望：核心管理员 1 · 未绑手机 0 · 无邮箱 0
```

**再加一条人工检查（最容易被忽略）：**

用**库管账号**登录前端，打开财务的 S4 结算页，**确认所有金额显示 `— —`**。
如果看到数字，说明前端直接查了基表——**这是最危险的一种错，因为它不报错**。
