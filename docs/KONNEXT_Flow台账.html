KONNEXT · 业务流分解 · 第二层

每条主线切成若干 Flow，一个 Flow 一个闭环

一个 Flow ＝ 人输入 → Agent 按说明查表接力 → 人 check。 它是交付单位：能单独开发、单独回归、单独上线。 所以要建的不是「一百多个 Agent」，是一次一个 Flow。 每个 Agent 只做一次单一输入输出，且必须有一个不是 Agent 的检查者（门／断／人／C）。 鼠标放节点上看它干什么、吃什么、吐什么、谁验它。

★ 先看这个：人 check 的负荷落在谁身上

你的模型里每个 Flow 都以「人 check」收口 —— 这是对的，但人的时间是有限的。 出口太密，人就会开始盲签，那时候监管点还在图上，实际已经失效了，而且不会报错。 下表按负责人 × 触发频率数出口。红格＝高频出口， 这些位置建议把出口从「人 check」换成「门禁」—— 门禁是确定性的，不会累，也不会因为今天单子多就放水。

这一层新暴露出来的三件事
① 高频出口会变成橡皮图章
「每天」和「每单」触发的 Flow，出口挂人工 check 是撑不住的。 建议这几个出口改成门禁 + 事后抽查：人不看每一单，只看断言报出来的异常单。
② Flow 之间也有交接
上一个 Flow 的出口就是下一个的入口（受理→排查→派工→完结→定价）。 这是部门内部的交接，v1 那张图只画了部门之间的。 同样的坑会在这里重演 —— 谁负责把状态推过去，要写死。
③ Flow 的状态存在哪
必须存在数据库既有的状态列里，不要在 Agent 编排层再存一份。 存两份 = 同一件事两个数字，迟早对不上，而且不报错 —— 和「项目料需求只存一份」是同一条规矩。
