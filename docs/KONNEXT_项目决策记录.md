## 1. 项目背景

KONNEXT 是澳大利亚（悉尼 / NSW）的智能家居集成公司，服务华语客户。要做**多部门协作的办公管理平台**，把售前、工程、采购、库管、财务、运维的工作流数字化，做到可验证、可校验、可修改。

**用户的两个核心担心**（贯穿所有设计决策）：

1. **架构过载** —— AI 设计太复杂，以后改不动
2. **逻辑错误长期不被发现**，导致错误决策

> 第 2 条是整个方案最重要的驱动力。实践中真正危险的 bug 全是"**不报错、只是数字悄悄错了**"那一类——
> 退库不进库存、未退料不进发票、视图绕过 RLS、SECURITY DEFINER 提权。
> **门禁测试一个都没抓到**，所以才有了 73 条不变量断言。

## 2. 十条架构原则（不可动摇）

1. **一个共享业务对象(project) + 只增不改的事实流 + 显式门禁 + 派生视图**。部门拥有的是"字段和门禁"，不是各自的数据库
2. **只增不改(append-only)**：原始输入不 UPDATE，改 = 插新行
3. **当前状态尽量派生**（视图现算），不存
4. **字段级所有权**：每个数据只有一个写入方 → 从根上杜绝覆盖冲突
5. **定格的落库，会变的现算**
6. **门禁由 DB 触发器强制**，UI 只是第二道。"没被拦住的门禁等于不存在"——再加半句：**"没被测到的门禁等于没有保障"**
7. **外部系统只读单向镜像**；**外部依赖绝不进门禁**（Google 挂了不能卡流程）
8. **通用能力抽离复用**（考勤、通知、清单），不做成某模块专属
9. **克制意识**：能用 SQL/公式就不用 LLM；AI 写实现、人定契约
10. **例外用「手动标记 + 填原因 + 留痕」过，不取消卡点**

### 三个判断口诀

**平铺还是建表**
- 固定几个、几乎不变 → 平铺进主表（联系人×3、楼层）
- 数量不定、种类可能扩展 → 单独建表（家庭成员、参建方、方案）

**分表还是共用**
- **规矩不同** → 分表（SM 要排队要签字，安装不排队不签字）
- **只是填的内容不同** → 共用一张表 + 类型字段（四类任务的清单）

**能自动扫全库的地方，绝不手列清单**
- 手列的清单一定会漏，而且漏了不报错（曾漏 13 个视图、漏售前身份）
- 项目标识追加、`security_invoker` 设置都改成程序化扫全库 + 断言守着

## 3. 技术选型与部署架构

```
浏览器（React + TypeScript + Vite）
    │  只调 API，不知道数据库存在
    ▼
后端 API（Next.js API Routes）
    │  ★ 在这里 SET app.account_id ← 取自服务器验证过的会话
    │    前端请求里带的任何身份信息一律忽略
    ▼
Supabase（PostgreSQL 15+）
    132 条 RLS 策略 · 73 条断言 · 全部业务门禁
```

**为什么必须有中间那层**：RLS 靠 `SET app.account_id` 判断你是谁。前端直连的话，**这句话由浏览器说了算**——改一行 JS 就能声称是核心管理员，全部权限瞬间失效。

**★ 必须 PostgreSQL 15+**：视图的 `security_invoker` 选项要它。

**绝对不能做的三件事**（写进开发规范）：
1. ❌ 前端直连 Supabase
2. ❌ Service Key / 连接串下发到浏览器
3. ❌ 前端直接查基表——**基表没有列级遮罩，只查视图**

**为什么选 TypeScript**：84 个视图的列名与可空性可从数据库生成成 TS 类型，改了 DDL 前端立刻编译报错。没类型的话，`sell_price_aud` 被遮罩成 null 而前端拿它做乘法，页面显示 NaN 且不报错。

### 外部依赖

| 依赖 | 状态 | 要点 |
|---|---|---|
| **Twilio 短信** | ★最要紧，未接 | **必须买澳洲手机号，不能用字母发送者 ID**（后者收不到 YES 回复）。2026-07-01 起澳洲 Sender ID 需 ACMA 登记，手机号可绕开。无密码登录**完全依赖它** |

| 报价系统 | **不对接** | 报价同事直接在系统里手填，`quote_source` 保持 `'manual'` |

## 4. 组织与权限

### 六个部门
售前 · 工程管理 · 采购 · 库管 · 财务 · 工程运维
（采购与库管是**两个部门**，可由同一人兼任 → 该账号同时挂两个部门）

### 账号三级结构

| 级 | 谁 | 账号由谁建 | 用什么 |
|---|---|---|---|
| **1** | 决策管理员，上限 **3** 个，其中 **1 个核心管理员** | 核心管理员自建；第一个账号自举 | 后台 + 决策页 |
| **2** | 部门负责人 | **只能由决策管理员建** | 后台（本部门范围） |
| **3** | 施工人员（含外包） | **只能由「工程管理」或管理员建** | **只有 App，不能进后台；只有上报权限** |

- **管理员不挂部门**（全局）；**施工人员也不挂部门**（只上报）
- **外包**：不计等级；账号由管理人员**代建**，建好后按第三级用
- **电工 / Builder / 客户：不给账号**，全部走短信与邮件

**登录与找回**
- ★ **全系统无密码**——表里不存密码，手机短信验证码（`auth_otp` 只存散列，一次性、有时效）
- 管理员额外**邮箱 + 手机双验证**，且必须绑手机、必须填邮箱（无邮箱直接拒建）
- **只有管理员可自主找回**；其余一律管理员重置，**全程留痕**（谁给谁改的、原值新值、原因）

**核心管理员**：全系统唯一 · 只有他能建/停用其他管理员 · **不能停用自己**（须先移交）

### 权限规则：读全部、写本部门

| 级别 | 读 | 写 |
|---|---|---|
| 决策管理员 | 全部（含敏感） | 全部 |
| 部门负责人 | **全流程业务数据**（敏感金额除外） | **只能写本部门归属的表**（`table_ownership`） |
| 施工人员 | 不给后台读；只看自己的工时与日结 | 只能写自己那几行 |

> **为什么读全部**：下游能查上游的流水，卡在哪儿一目了然。系统自动推进之外还有人在推。

**部署方式**：应用只用**一个数据库用户**，登录后 `SET app.account_id`；权限完全由**账号 + 部门表**决定。
未登录（account_id 为空）→ 按最低权限处理，**失败即关闭**。

**⚠️ 兼任风险**：`v_dual_role_alert` 点出"同时管采购与库管"的账号——这类账号**可以自己下单、自己确认到货**，「盘点人不能自己批自己」那道门也会失效。**待决策**：是否要求到货确认与盘点审批交他人复核。

### 金额可见性：五类，各看本职

| 类别 | 谁能看 | 守卫函数 |
|---|---|---|
| **薪酬** | 财务＋管理层 | `fn_can_see_salary` |
| **成本与利润率** | 财务＋管理层 | `fn_can_see_margin` |
| **采购价与毛利率** | 采购＋管理层 | `fn_can_see_purchase_price` |
| **客户合同金额** | 财务＋**售前**＋管理层 | `fn_can_see_customer_amount` |
| **库存成本单价** | **库管**＋采购＋财务＋管理层 | `fn_can_see_stock_cost` |

> 售前能看合同金额（签约价是他填的）；库管能看库存成本（出库单价是他填的）。
> **业务流水互相可见 ≠ 钱的数字互相可见。**
> 要放开某一项，在对应函数里加 `OR fn_has_dept('xxx')`。
> `v_money_guard_map` 列出每个带钱的视图由哪个函数看守，改动时照它自查。

### ⚠️ 三个曾踩过的权限坑（都是"不报错只是全放开"型）

1. **`SECURITY DEFINER` 里的 `current_user` 变成函数所有者**。原先写了 `pg_has_role(current_user,'konnext_admin')`——在 SECURITY DEFINER 中 `current_user` 是 postgres（超级用户），于是**每个人都被判成管理员**，库管改签约价一声不响就成功。已去掉所有 `pg_has_role`
2. **权限函数必须 `SECURITY DEFINER`**，否则 `fn_me()` 查 `app_account` → 触发该表 RLS → 策略又调 `fn_me()` → 栈溢出
3. **视图默认按【视图所有者】执行，RLS 整个被绕过**。PostgreSQL 视图默认 `security_invoker=false`。**所有视图必须 `ALTER VIEW ... SET (security_invoker = true)`**，DDL 末尾有自动补齐的 DO 块，断言 `INV-SEC-01` 守着

## 5. ★★ 项目归属三态规范（最重要的横切规则）

> **系统内所有流水／报告／报表／通知／任务／成本／收款／付款／报销／收入／支出／利润，
> 必须有具体项目。例外只有两种，且都必须明确标记，绝不许靠留空糊过去。**

| 三态 | 含义 | 要求 |
|---|---|---|
| `project` | 属于具体项目 | **必须填 `project_id`** |
| `company` | 公司级 | **明确标记**；通知/报销还要填 `scope_reason` |
| `untraceable` | 无从追溯 | **明确标记 + 提示人工确认**，系统不猜 |

**`project_scope_registry` 归属登记表**——每张表属于哪一类、怎么追回项目：

| 归属类型 | 表数 | 举例 |
|---|---|---|
| 项目必填 | 19 | 收款/出库/工时/变更/维护/订阅/RMA/交付/SM |
| **项目 或 明确公司级** | 5 | 通知 · 部门交接 · 交接留痕 · 问题上报 · **报销** |
| 经父表可追 | 6 | 收款明细→milestone · 出库明细→出库单 |
| **跨项目·可追** | 5 | 日结 · 每日上报 · 月工资单 · 倒休 · 路程预估 |
| 公司级 | 4+1 | 采购单 · 盘点 · 物料 · 汇率 ·（离职清算=人员级） |
| 人员级 / 配置 / 审计 | 19 | 账号 · 人员 · 阈值 · 假日 · 文档 · 断言 |

**跨项目怎么追**：`v_daily_projects`（某人某天涉及哪些项目 = 打卡 + 四类任务派工，合并去重）。在它之上：
- `v_daily_payroll_detail` —— **挂起的日结带"补录线索"**：「待负责人补录 · 当天派工：0142 / 0180」；
  当天既无打卡也无派工 → 「**★无从追溯：需人工确认**」
- `v_payroll_month_projects` —— 月工资单按周期内各项目**工时占比分摊**

**★ 项目标识贯穿全系统**
- `project.display_label` 生成列 = `编号 · 名称或Suburb`
- `v_project_label` 规范视图（`display_label` / `addr_suburb` / `addr_full` / 业主 / Builder / 电工）

  —— 程序化扫全库，新增视图重跑 DO 块自动补上；断言 `INV-UI-01` 守着**一个都不许漏**
- `v_project_directory` 项目总目录：六个部门的项目列表页**共用这一个**

> 实际工作里没人靠 `KX-2026-0142` 认项目，大家说的是「Cherrybrook 那家」。所以地址必须带出来。

**★ `v_open_tasks` 悬而未决总表**——管理人员打开这一张就够了。汇总 11 类挂起事项，
**前三列固定为 项目编号 / 项目地址 / 项目标识**，无项目者显示「公司级」或「★无从追溯」，绝不留空。

## 6. 完整业务流程

### ★ S1~S4 与 SM1~SM4 是两套东西，别混

| 编号 | 是什么 | 内容 |
|---|---|---|
| **S1~S4** | **收款阶段** | S1 定金 10% ｜ S2 物料款 40% ｜ S3 人工款 40% ｜ S4 尾款 10% |
| **SM1~SM4** | **工程现场会议** | SM1 进场 ｜ SM2 布线交流 ｜ SM3 检查布线 ｜ SM4 封板核对 |

> **S 是钱，SM 是会。** 财务说"S2 没到账"和工程说"SM3 已完成"是两件事。
> （决策看板 Demo 里把工程阶段写成 S1~S4 是那边的笔误，以本契约为准。）

### 主链路

```
【售前】七步：①讲功能 ②全功能设计 ③讲解修改 ④出Draft ⑤讲Draft ⑥最终定价·客户签字 ★方案定版 ⑦已收定金
   ↓ 门禁：第六步没签 → 不能置"已签署报价"、不能进施工
【财务】S1 定金 10%   ↓ 门禁：定金没到 → 工程不能进场
【工程】SM1 进场 → SM2 交付Finish给电工·★电工签字 → 〔电工Rough-in布线〕
   → SM3 检查布线·★双向签字·★登记变更   ↓ 门禁：SM3 完成才能发 S2
【财务】S2 物料款 40%   ↓ 门禁：S2 结清才能下单 ／ 才能出库放货
【采购】下单 → 到货入库（公司级）
【库管】★出库 —— 物料在这一刻才落到具体项目 + 提货人 + 短信确认
【工程】预配 → 发货 → 〔封板〕→ SM4 封板核对出线   ↓ 门禁：SM4 完成才能发 S3
【财务】S3 人工款 40%（★与电工补线解耦）
【工程】安装调试（一趟趟去）  ↓ 门禁：必须 SM4 之后
   → ★整体完工 = 剩余清零 + 负责人确认，两个都要
【财务】S4 尾款 10% + 可计费变更 + 未退料
【工程管理】看"工程流水账"人肉确认交付条件（系统不代替判断，但留痕）
【工程】交付 Handover  ↓ 门禁：S4 结清（硬卡无后门）+ 已确认 ready + ★客户签收
   → 完成瞬间：回写交付日 · 状态转 delivered · ★工程利润率定格
   → ★交付过程中签【业主订阅】（归运维）
【运维】技术维护（长期）+ 订阅续费
   → 拒付 → 财务标记 → ★项目级全面停服 → 市场发声明 → 90 天后停用服务器
```

### 项目状态（9 态）+ 卡住天数

`engaging` 接洽中 · `to_contact` 待联系 · `quote_signed` 已签报价 · `deposit_paid` 定金已收 ·
`in_construction` 施工中 · `delivered` 已交付 · `maintaining` 维护中 ·
**`bid_lost` 留标** · **`stalled` 已烂尾**

| 失败态 | 定义 | 门禁 |
|---|---|---|
| **留标** | 参与投标/谈判但未中标，或方案发出后无反馈 | **有任何一笔合同款已结清就不许置留标** |
| **已烂尾** | 已在施工阶段无法继续，**且尚未进入维护** | **已交付的不许置烂尾**；**未签约的也不许**（那叫留标） |

**卡住天数**：`project.status_since` 状态一变自动重置 + `status_stall_threshold` 一状态一行配阈值。
默认：接洽 45 · 待联系 30 · 已签报价 14 · 定金已收 21 · 施工中 120 · 已交付 30 · 终态不设。
`v_project_stall` 算停留天数；`v_risk_board` 汇总留标/烂尾/卡住/订阅逾期。

## 7. 各模块最终结论

### 7.1 售前立项
`project`（编号/地址/坐标/联系人×3平铺/佣金/房屋用途类型/施工阶段/楼层×5/屋顶/七步时间戳/签约价/定金/**免责维保月数 0~12**）
+ `household_member` + `project_party` + `solution_option`（有线无线单列 + 协议 + 预算 + **有无 KNX/地暖**）

- **第六步签字 = 方案定版信号**，没它后续全部动不了
- **定金只有财务能写**，售前只读（字段级所有权第一个落地）
- 乐观锁 `version`：冲突提示「项目已被他人修改（期望 1，实际 3），请刷新重试」
- `has_knx` / `has_floor_heating` 决定 **SM2 清单上要不要显示"带 KNX 线/地暖线"**
- 坐标既给地图，也当**考勤围栏圆心**

### 7.2 四类任务（顺序 = 现场先后）

| 顺序 | 任务 | 特有规矩 |
|---|---|---|
| **①** | Site Meeting | SM1→2→3→4 顺序硬卡；SM2 电工签字、SM3 双向签字；**不报那 5 类问题** |
| **②** | 安装调试 | 必须 SM4 之后；**不签字**；超时要报问题 |
| **③** | 交付 | 必须 S4 结清；**客户必须签字**；一项目一次 |
| **④** | 技术维护 | **只受理已交付项目**；默认挂维护单，急事可无单派工+填原因 |

**四类共用**：出发前清单 `job_checklist`（靠 `job_kind` 区分）· 工时考勤 `work_log` · 通知 `notification`

> 任务表分开是因为**规矩不同**；清单合并是因为**规矩相同**（适用项全勾才放行）。

**SM 各自特有**
- SM1：进度照片、记录牌照片、见到了谁、采集分包商进参建方表
- SM2：交付 Finish 给电工 → **电工单向签字**；清单 6 项（KNX/地暖为条件项）
- SM3：以 SM2 的 Finish 为准检查 + **双向签字** + **登记变更**；整改只记"已告知+电工签字"，不追踪落实
- SM4：只带最新图纸；人工核对出线；**缺线只拍照通知，不自己动手**

**老项目后门**：`na_flag` 标不适用 + 填原因 → 后续 SM 放行。走一次记一次。

**安装剩余项五态**：`pending` / `done` / `cancelled`(填原因) / `suspended`(填原因+卡在谁) / `to_variation`(关联变更)
> **"清零"≠"全做完"**——后三种也算清零，但每次都留着名字和理由。
> 负责人点完工时看到的是"3 项：1 项客户取消、2 项等空调队"，签的是明白账。

**交付前的工程流水账**（视图，不新建表）：时间轴维度 + 人员维度（KPI 用）。
**交付条件人肉确认，系统不卡**——"干得够不够好"没法用规则表达。但**谁、何时、看着哪版数据点的 ready 要留痕**。

### 7.3 变更 Variation

**只在 SM3 产生，只留痕。** 类型：多加 / 减少 / 移位（移位在图上标，不记原坐标）。
登记后**自动知会设计、采购、财务** + 留痕。**金额和工时在 SM3 都不碰。**

**计费规则**
- **加 / 减 → 计费**（客户变更）
- **移位 → 不计费**：移位是电工装错位置，属整改。仍登记留痕，但填金额直接拒
- **人工不单列**：物料售卖价 = 成本 ÷ (1−毛利率)，**毛利里已含安装人工**，变更跟着物料走
- **工时超支不挂客户**：实际 vs 预测的差额是我们效率问题，吃工程利润率

**估价 = 外部系统**：财务 + 库管依据工程与 SM 记录**在外部手工计算**，填回 `settle_amount`。
留痕四件套：`settle_source` / `settle_ext_ref` / `settle_by`+`settle_at` / `settle_note`。
**★ S4 发票已发出后，变更金额不许再改**——要改就 S4 开 v2 重发。

**未退料并入 S4**：S4 开票**前**跑 `fn_settle_unreturned(项目)`，把未退料按售卖价转成正式变更记录。
明细表亮 `need_settle_unreturned` 提醒；**S4 发出后不许再追加**。
> 这是补的一个洞：未退料原先只是视图，没进 `variation` 表，导致明细算 56513.83、发票自动算 54500，**差 2013.83 且不报错**。

**变更争议不追溯**：交给人处理。系统只摆事实（谁手里多少件、金额多少、Builder 何时收到告知）。

### 7.4 采购与库管（两个部门）

```
【采购】对供应商下单 → 到货入库（公司资产，不属任何项目）
   → 【库管】出库 ★这一刻才落到具体项目 → 提货人短信确认
```

**物料主表 `material`**
- 品类(功能) / 协议 / 物料名(内部型号) / 型号(供应商型号) / 供应商 / 规格颜色
- **每个规格颜色是独立物料**：白面板 M0001、黑面板 M0002 各有各的库存与红线
- **`display_name` = 物料名 + 规格，自动生成**。两行的 `internal_name` 完全相同，报表一扫就看串 → **所有对外呈现一律用 `display_name`**
- **C1 定期备货**：每半月集中采购，设 `reorder_point` 红线
- **C2 按需采购**：本地/极易获取，**严格不设红线**（填了直接拒），SM 确认需求后采购，客户最长等两周
- 三币种采购价 + 运输成本；**利润率口径 = 毛利率**，售卖价 = 成本 ÷ (1−利润率)
  - ⚠️ 利润率必须 < 0.95：填 1 除以零、填 >1 算出负价，且不报错
- 维保期(月)：厂商固定期限，**与工程变更 `variation` 无关，勿混用命名**
- 调价/调利润率**自动留痕**

**增 / 划掉 / 恢复 / 彻底删除**
- **划掉**（软删除）：`active=false`，界面画横线。**必须填原因**
- **恢复**：`archived_*` 不清空——划掉过这件事本身是历史
- **彻底删除**：**只有从未产生任何流水的物料才允许**，且必须先划掉（防手滑），删除动作进审计日志
- 划掉后**不再被任何系统调用**（采购/出库/期初全拦），但**历史记录一字不动**
- **划掉但仍有库存的货不能从报表消失**（`v_archived_with_stock`），否则成账外物资

**汇率 `fx_rate` ★只增不改**：每次抓取插新行，当前取最新 → 历史汇率永久可查。
抓不到时人工填标 `manual` 并写原因；`is_stale` 超 3 天亮灯，**不静默用旧值**。

**★ 库存全部现算，不落库**
```
当前库存 = Σ到货 − Σ出库 + Σ退回(好料·未被拒收) + Σ盘点调整(已审批)
```
> 用户最初想加"库存"一列。**不能加**——存成列就有两个真相，迟早不一致且不报错。

**期初库存移库**（公司不是从零开始的）
- 采购单加类型 `opening`，把仓库现有存货**当成一次到货**录进来 → 公式不用改，来路可查
- **一个物料只能做一次期初**（做两遍库存凭空翻倍，**上线时最容易犯又最难发现的错**）
- 工具：`期初库存_填写模板.csv` + `导入期初库存.py`（默认只试算，`--confirm` 才写；整批一个事务，要么全成要么全不写）

**出库 `stock_out`（★物料落项目的时刻）**
- 强关联三要素：出库时间 + 项目 + 提货人
- **提货人只能二选一**：自己的工程人员 或 **本项目立项时录入的参建方**（拿别项目的电工来提 → 拒）
- 姓名手机号**定格**在出库单上；没手机号直接拒（发不了短信）
- 出库数超过库存 → 拒
- **★ S2 门禁在出库，不在采购下单**：采购是公司级行为，不能因某项目没付钱就不给仓库补面板

**提货短信双向确认**（`sms_2way` / `replied_yes` 占位在此首次启用）
- 出库即自动生成中英对照提货清单短信；**一张出库单一条短信**（加明细时更新内容，不是加一行发一条）
- 已发出的短信不再改动；回 `yes` → 出库单自动置"已接收"

**★ 给 Builder 的物料发放告知**（无 Builder 则发业主）
出库给外部人员时自动发出，写明何时把什么发给了谁、逾期未退将计入 Variation。
**这不是通知，是责任凭证**——没有它，业主凭什么认未退料那笔账。

**退库 / 拒收**
- 好料 `good` → 回可用库存；坏料 `damaged` → 不回库存，**自动转 RMA**
- 退库数不得超过该人在本项目名下未退数量
- **拒收必须三件齐全**：谁拒的 + 原因 + 货现在在谁名下（缺一即拒）。责任仍归对方

**★ 未退料一律先计入客户 Variation**
> 这不是记账偷懒，是**拿客户当审计员**。工地物料流向看不住，靠自查成本高又查不全；
> 变更单一发出去，客户自然来对账，异常就浮出来。客户 argue 即触发追溯。
> 前提：Variation 到 S4 才结算，中间有足够时间 argue。
> **发错料 / 现场条件变了 / 电工装坏了——一律先记客户账**，不在系统里预先分责任。

**RMA 坏货**
- 坏货**必须退回仓库才认**，不退则责任人自担
- 记录：项目/退货人/物料/退回时间/包装是否完整/配件是否缺失/**损坏原因**
- **保修起算 = S2 结清日**；供应商与保修自动带出
- **在保 → 返供应商**，四道跟踪防"退回去就不还了"：寄出→已接货→已返还→修理费/运费。**顺序硬卡**
- **过保 → 报废**；积压可清理，但**必须记录操作人与原因**
- **成本吸收**（登记当时定格）：未交付 → 项目工程成本；已交付 → 长期运维成本

**盘点（账实不符）**
- 不直接改库存，**记一笔盘点调整流水**
- **系统数在盘点那一刻定格**——不存的话事后再出入库就永远还原不出"当时差了多少"
- **盘亏必须填原因**；审批线 A$200，超过必须审批，且**盘点人不能自己批自己**
- **审批前库存不受影响**；审批后自动调整；**已审批不能再改明细**

### 7.5 财务

**全公司一套应收规矩**：`payment_milestone` 加 `kind` = `contract`(S1~S4) / `maintenance` / `subscription`。
收款明细、结清判定、Invoice 版本化、现金/走账、GST 全部共用。
> 不合并的话现金和 GST 要写两遍，**税务口径两套账，风险不小**。

**应收金额：发出即定格**
- 发出前跟着签约价现算浮动（签约价×比例，S4 叠加**可计费**变更）
- **一点"发出"就焊死**——客户手里那张纸和系统永远对得上
- 要改 → `invoice_ver` +1 重开新版

**结清：系统算，财务点**

| 项 | 谁决定 |
|---|---|
| 已收 / 还差 | 系统现算 |
| `partial`（收了不够） | **系统自动判** |
| `settled` | **只能财务点** |
| 足额 | 直接放行 |
| **不足额** | 放行，但**必须填原因**，**批准当时的差额定格落库** |

> 差额定格的理由：以后收到零头，现算值会变 0，当时的批准记录就糊掉了。

**超期：只提示，不作废合同**

| | 从哪算 | 谁看 |
|---|---|---|
| 本期超期 | 最后一版 Invoice 发出 | 催账 |
| **账龄** | **第一版发出** | 管理层，**改版抹不掉** |

标准 30 天。市场 + 财务介入催账。
> 为什么要两个数：改版重发会让超期归零，而催账时改金额重发本是常规操作。**账龄堵住这个口子。**

**拒付：财务手动标 → 项目级全面停服**
不用等 30 天；停整个项目不是单张单；**任何新任务派不出去**；90 天后提醒停用服务器（市场发声明，**人去执行**）。

**收款细节**：一笔款可分多次收、现金走账混合。**GST 单列**（走账默认 10%，现金默认 0，可手改）。
⚠️ 现金/GST 涉及税务合规，系统只如实记录，**报税以会计/税务顾问为准**。

**★ 报销 `expense_claim`**
- 三态归属；公司级/无从追溯**必须填原因**
- 提交必须有收据照片；**不能自己审批自己的报销**
- 已批准的进项目成本（`v_project_expense`）；公司级报销单列（`v_company_expense`）

**S4 结算**：`v_s4_settlement` 总表 + `v_s4_line_items` 逐条明细。
**不计费的行也要显示**（灰色 ✗）——客户问起来有交代，不显示反而像漏了。
每条可追到来源、登记人、外部单号、**计算依据原文**。

### 7.6 运维与维保

**★ 维护单只受理【已交付】项目**——未交付一律不予处理，**建单和派工两道门都卡**。
交付前客户发现的问题属于安装还没干完 → 走剩余项或变更登记。

**★ 真实流程：先上门，后定价**
```
受理建单(还不知道多少钱) → 派工上门 → 修完【当着客户面确认归因】
→ 【客户签字确认当日服务内容】→ 才可离开
→ 办公室按【工程人员报回的归因 + 时长】定价 → 开票 → 收款结案
```
单据状态：`open → in_progress → invoiced → paid_closed`

**现场三样缺一不可**（否则任务点不了完成，人不能走）：
① 故障归因，当着客户面确认 ② 当日服务内容（客户签的就是这段）③ 客户签字

**人没去过不许开票**——定价要靠现场归因与时长。

**报修受理**：`reported_at`（**允许"未知"**）/ `report_channel` / `taken_by` / `report_note`（客户原话）
> 若空着就默认取建单时间，响应时长永远显示 0 分钟——**看起来好看，但那是假的**。宁可显示"算不出来"。

**口头预估 `estimate_amount`**：工程管理填，**不参与任何计费**，实际以发票为准；填了自动留痕。

**★ 故障归因·四类统一词表**

| 值 | 含义 | 后果 |
|---|---|---|
| `human` | 人为损坏 | 免责维保**不覆盖**；责任人承担，不索赔 |
| `product_defect` | **产品缺陷** | 免责期内全免；**在保 → 返供应商索赔** |
| `wear_out` | 自然老化 | 免责期内全免；过保报废 |
| `force_majeure` | 不可抗力 | 走保险或客户自担 |

> 统一前三处各用一套词表。**"非人为"和"产品缺陷"不是一回事**——面板自己坏了可能是批次缺陷（该索赔），也可能是正常老化。
> 统一后：**现场填一次，RMA 直接继承**。`v_rma_action` 按归因+在保给出处置建议。

**★ 维护有两种上报，别混**

| 上报 | 何时 | 内容 | 不填后果 |
|---|---|---|---|
| **现场·故障归因** | 收工前，当着客户面 | 上面四类 | ⛔ 走不了 |
| **当日·问题上报** | 当夜，跨项目一条 | 研发/产品/市场/标准化/工程安排 | ⛔ 提交不了 |

归因决定**这单收不收客户钱**；上报决定**管理层看到什么问题**。

**两套维保钟**

| | 免责维保 | 物料保修 |
|---|---|---|
| **起点** | **交付之日** | **S2 结清日** |
| **时长** | 0~12 个月（售前手填） | 各供应商不同（采购单填） |
| **覆盖** | 非人为：**人工+物料全免** | 只管物料 |

**期外收费**：物料**没过保** → 只收人工；**过保** → 人工 + 物料。财务报价。
**★ 不做设备台账**——维保只查该项目 S2 收款日期。
⚠️ 物料保修从 S2 结清就烧，**施工拖越久客户拿到手时保修烧掉越多**。交付当天显示"物料保修剩余 X 个月"。

**免责维保单开 $0 Invoice**：金额 0 照开发票，列明人工多少小时、换了什么件、应付 $0。
**免费不等于白干**——客户看得见值多少钱；对内一年免掉多少单列一栏。

### 7.7 业主订阅（归运维）

**交付过程中签**，业主愿意就进订阅流程。

| 项 | 规则 |
|---|---|
| 档位 | **1~5 档，第 5 档 = 不订阅** |
| 年费 | 运维填；1~4 档必填且 >0；**第 5 档不得有年费与期间** |
| 各档含什么服务 | **系统不管**，全在线下 |
| 门禁 | **只能建在已交付项目上** |
| 收款 | `kind='subscription'` |
| **计入利润率** | **不计入**。另看 `v_subscription_rollup` |

**四色状态**（`color_token`，前端直接用）：生效中 `green` · 即将到期 `amber`（30 天内）· 已逾期 `red` · 未订阅/已退订 `grey`
**已退订的历史已收仍计入累计**，只是不计年化与活跃数。

### 7.8 考勤 · 路上时间 · 午餐

**围栏**：默认 100 米（按项目可调），圆心 = 项目坐标。入场**定位优先、拍照兜底**；拍照的记录在案，频繁拍照 → 标记追溯。
离场：现在定时抽查，出围栏标"疑似离开"；将来原生 App 后台持续定位自动离场（**字段已设计好，升级时结构不变**）。

**路上时间 traffic slot** = 上一站离场 → 下一站入场，逐段编号。
**全自动派生，人不用填**——想少一段就得在打卡上动手脚，那条路已被围栏/拍照/留痕堵死。
起点 = 当日第一站**入场**；末站回程不算。

**★ 付薪按首尾**（澳洲规矩，路上不能克扣）
```
当天付薪时长 = 最后一次离场 − 第一次入场 − 午餐
```

**★ 午餐：自动扣，不打卡** —— 30 分钟无薪；首尾满 5 小时才扣；**锚点 12:00**。
> 不打卡是因为打卡能忘点/晚点/假点；**必须扣**是因为不扣的话，准点上下班 8 小时的人也会被算成超时 30 分钟——**天天触发，门禁作废**。

**成本分摊**：**路上成本摊给下一站项目**；午餐扣在锚点所在那一段。
**项目成本口径必须跟发薪口径一致**，否则利润率失真。

**Google 预估：两版都存死**

| 显示 | 何时查 | 回答什么 |
|---|---|---|
| 计划预估 | 派活时按**计划**出发时间 | 派活估时准不准 |
| 实际预估 | 收工后按**实际**离场时间 | 那个时段本该开多久 |
| 真实耗时 | 打卡现算 | 实际开了多久 |

**必须连"查询时用的出发时间"一起存死**，否则拿今天的路况审昨天的人。
**只给工程管理看，不影响发薪；查不到就空，不进门禁。**

### 7.9 每人每天上报

**挂"人 + 日期"，不挂项目**——一人一天可跑几个项目，上报**横跨项目，每天一条**。

**两条超时线**（任一超 30 分钟即强制）

| 线 | 拿什么比 | 抓的是 |
|---|---|---|
| **计划超时** | 在场总和 vs 当天派活计划总和 | **活比预想的难** |
| **工时超时** | 付薪时长 vs 标准 8 小时 | **加班了** |

> 分开是因为：堵车导致下班晚 → 工时超时（该付加班费，是事实）；活干不完 → 计划超时（要写原因，是问题）。

**五类问题**：研发 / 产品 / 市场 / 标准化 / 工程安排
- 不超时自愿填 · 超时不填不许提交 · **SM 不报**（SM 不存在这 5 类问题）· **填写时间不计工时**
- ★ **必须落到项目，或明确标 `is_company_level`**

### 7.10 工资：三种制度

| | 月薪制 | 时薪制 | **外包 contractor** |
|---|---|---|---|
| **发薪** | 每月固定，**不发加班工资** | 付薪时长 × 时薪 | **固定日薪，去了就一天** |
| **周末/公共假日** | 整天算加班 | 整天算加班 | **没这个概念** |
| **加班** | 累计 → **倒休** | 按倍数付 | **没有加班** |
| **成本时薪** | **人工换算手填**（不填拒绝建人） | 就是发薪时薪 | **系统自动算 = 日薪 ÷ 参考时间** |

**外包也进 `eng_staff`**（这张表实为"人力资源"）——考勤、工时、项目成本全套照用。

**★ 时薪计算参考时间 `ref_minutes`**：这**不是**"承诺工作多久"，是**算成本时薪用的除数**。
例：日薪 510、参考时间 10 小时 → **成本时薪 51**。
⚠️ **实付与摊入会有差额**（发薪按整日薪，项目成本按成本时薪×实际在场）。`v_contractor_cost_gap` 把差额摊出来，**让偏差看得见**。

**日结：当夜 0 点定格**，一人一天一条，行数按实际出工天数走。
**定格即不可改**——补录只能滚到下月补发。**制度、发薪时薪、成本时薪、加班倍数一并定格**（8 月加薪不影响 7 月）。

**没记录的那天**：**不扣钱**（澳洲 Fair Work 不允许惩罚性扣薪，且打卡失败常常不是人的错），但**挂起不发**，须**负责人补录 + 填说明**才放行；同时永久进 KPI。
> 压力传导到管理层，比扣工程人员合法也有效。

**加班判定**：平日超标准工时的部分 + **周六周日整天** + **公共假日整天**。

**加班倍数**：**工程管理手动设置**，两层——全局默认（`eng_setting` 四个键）+ **按人覆盖**（`eng_staff.ot_rate_*`，NULL=跟全局）。
- **不许设成低于 1**；**当天倍数随日结一并定格**；**改倍数就是改钱**，改动全进审计
- ⚠️ 现在全是 1.0（加班不加倍），**按你们实际的 Award / EA 填**

**公共假日按 NSW**，`public_holiday` 已录 2026 全年 **12 天**（核对自 Fair Work 官方名单）。三个易错点：
- ⚠️ **Anzac Day 落周六，NSW 不补假**（补假只有 ACT/WA；部分网站写 NSW 13 天是错的）
- ⚠️ **8 月第一个周一的 Bank Holiday 只适用银行**
- ⚠️ **Easter Saturday 是 NSW 特有**，别照别州抄
- **一年更新一次**；`v_holiday_coverage` 剩不到 90 天预警。**宁可空着也不要凭记忆填错**

**倒休**：**不存余额存流水**（`toil_ledger`，只增不改），余额视图现算。**按出工日归期**，不按记账时间。

**月度**：周期 = **上月 21 日 → 本月 20 日**，21 日封账即发放。**只做日结加总**，不再存一遍明细。

**入职/离职**：`hired_at` 必填、`terminated_at`。**入职前、离职后一律不生成日结**。

**离职清算**：系统算出「未休倒休 × 离职时成本时薪 = 应结多少」并定格；**付不付、付多少由人定，但不一致必须填原因**。清算后加一条冲抵流水冲平（**只增不改，旧记录一条不删**）。
⚠️ 涉及雇佣法，**以雇佣合同与会计/劳资顾问意见为准**。

### 7.11 文档库（★版本化）

### 7.13 成本与两个利润率

**人工成本链**
```
分母(预测工时) ← 报价系统手填 → project.planned_labor_hours
分子(实际成本) ← (在场工时 + 路上时间 − 午餐) × 成本时薪
消耗% = 实际/预测 → 推进中现算，交付定格
```

**★ 利润率口径（定稿）**
```
利润   = 合同额 − 材料 − 人工 + 维护净额
利润率 = 利润 ÷ 收入基数
```
- **材料**按【出库明细】归集（不是采购单）——**库存里没发出去的货不算进项目**
- **人工**按 work_log × 成本时薪
- **维护净额** = 维护收入 − 维护成本
- **★ 订阅收支不计入**
- 四档配色：`healthy ≥55%` / `warning 45–55%` / `breach 0–45%` / `loss <0`

**★ 三处特殊处理**（修掉"未开工显示 100% healthy"这个会误导决策的问题）

| 情形 | 处理 | 档位 |
|---|---|---|
| 未开工（无材料无人工） | **不显示利润率** | `not_started` |
| 留标 | **不显示** | `bid_lost` |
| **已烂尾** | 收入基数换成**实收合同款** | 按实算 |

> 烂尾意味着钱收不全，按合同额算利润率是自欺（会显示 +66%，实际 −237.6%）。

**工程利润率**交付当天定格落库；**长期利润率**视图现算，单列"免责维保共免掉多少"。
**RMA 成本吸收**：未交付 → 项目工程成本；已交付 → 长期运维成本。

## 8. 定格 vs 现算（最容易搞错的分界）

### 定格落库（历史事实，以后不能变）

| 数据 | 何时定格 | 为什么 |
|---|---|---|
| 应收金额 | Invoice 发出时 | 客户手里那张纸不能变 |
| 结清差额 | 财务批准时 | 后来收到零头，现算会变 0，批准记录就糊了 |
| 账龄起点 | 第一版 Invoice 发出 | 改版不能抹掉 |
| 工程利润率 | 交付当天 | 交付后成本还在动 |
| 是否免责维保覆盖 | 结案时 | —— |
| Google 路程预估 | 查询时（连出发时间一起） | 路况会变，不能拿今天审昨天 |
| 每日超时判定 | 提交时 | 后补工时不改历史判定 |
| **日结工资** | **当夜 0 点** | 含制度、发薪时薪、成本时薪、加班倍数 |
| 盘点账面数 | 盘点那一刻 | 否则"当时差多少"永远还原不出 |
| 文档已发放版本 | 发放时 | 电工签的是哪一版 |
| 离职倒休应结 | 离职清算时 | —— |
| 出库/退库单价 | 出库时 | 喂项目成本 |

### 现算不落库（会变的东西）

距今天数 ｜ 已收/还差 ｜ 超期天数与账龄 ｜ 路上时间 ｜ 每人每天在场/首尾/付薪 ｜
项目人工成本 ｜ 人工消耗% ｜ 工程流水账两个维度 ｜ 库存与在途 ｜ 安装剩余统计 ｜
两套维保到期 ｜ 长期利润率 ｜ 停服天数 ｜ 倒休余额 ｜ 外包实付与摊入差额 ｜
状态停留天数 ｜ 订阅状态与年化

## 13. 工作方式约定

> **定稿记录**：2026-08-01 用户原话「售前的UI样板我基本满意了」→ 本章即定稿口径，
> **是后续所有部门页面的模板**；再改动须用户明确提出并在此追记。

> 本章是后续所有部门页面的**模板**。原型：`docs/KONNEXT_UI原型.html` → 售前大表。

### 结构
- **整个售前 = 一页长大表**；导航（十一轮定名）：**项目列表**（=大表）· **项目状态表** · 设置
- **项目状态表**（十一轮加）：上半左**扇形图**=在途项目（非签约非流标）状态占比（有序阶段=同蓝系浅→深，
  逐片直标+旁表数量兜底，调色板过验证脚本）；上半右**堆叠柱**=所选时段立项去向（一根柱三段：
  绿=已签约 #047857 · 红=已流标 #dc2626 · 蓝=待签约在途 #2563eb，周/月/季/年方块切换，段间白隔+直标数量，
  三色过 CVD 验证）；下半「全部+6+1」状态过滤，过滤出的表格与项目列表**完全同款可操作**（共用 preBigTable）
- **近 12 个月逐月柱 = 只一张「每月立项项目成交图」**（十四轮两张 → 十八轮用户定删掉「新立项数量（市场增长）」单柱图）：
  三段柱（绿签约/红流标/蓝在途），**柱顶数字 = 当月新立项总数**（没有就是 0，空月柱显 0）——一张图同时看增长与转化；
  **去向永远回填到立项月份的柱上**（十七轮定）：26-05 立的项哪怕 9 月才流失，红段也记在 26-05 那根柱。
  项目持续多月也只出现在立项那个月，**不是积累量、不重复计数**（标题与帮助明示）；
  当前月加粗、悬停各段；**柱高按当档最大值自适应等比缩放**（十五轮定：数值再大也不溢出面板）
- **图表联动 = 全部现算**（十三轮定，十七轮改口径）：扇形/去向柱/两张月度图**全部由项目数据现算**
  （立项日期 + 当前状态；模拟历史与「改动算今天」的增量补丁已删）——改 6+1 勾，成交图在该项目**立项月份**
  的柱上换色、别的月不动；立项建档当月柱 +1；周/月/季/年去向柱同样按立项日期取窗口。
  与正式系统同口径：按 `project.created_at` 归月分组、按当前状态拆段，现算不落库
- **默认只显示四大项**：项目 ｜ 售前状态 ｜ 预测报价 ｜ 签约（单号·工时·定价·定金）——
  其余列组（联系人/关系人与佣金/房屋/注释）用**开关按钮**调出；City / State 两个下拉过滤
- 地址列：**黑体 = 客户项目昵称**，灰字地址**带州缩写**；前两列冻结，其余横向滚动；列组间 2px 分隔线
- **实时搜索（逐字刷新）**：编号/昵称/地址（含 City/State）一框全搜，打一个字过滤一次；全公司项目列表同款——大表类页面标准件
- **立项时间列 = 编号后标配**（十六轮定）：**凡出现项目编号的表，编号后一列固定是「立项时间」（年/月/日）**——
  售前大表进冻结区（跟编号一起钉住）、全公司项目列表、总览卡点表已同步；立项引导完成时自动落当天；
  对应 `project.created_at`（契约已有字段，不新增欠账）

### 售前状态 = 6+1 个勾（全部手填，系统不猜）
- 顺序：**接洽中 → 设计中 → 报价中 → 修订中 → 待签约 → 已签约**；第⑦勾（红）= **已流失**（流失=流标同一回事，勾上即终态整行归档变灰；原「留标」并入已流失）
- **勾到哪 = 处于哪**：最后一个勾即当前状态（蓝高亮）；已签约只亮 6 个勾；每勾**定格日期**（悬停可见）；勾下 45° 斜排状态名
- **勾可点选且支持反选**（十轮定）：点下一格=推进；**点当前格=反选回退一步**（人为点错可回退）；点更早的格=直接退回；
  第⑦勾点一下流失、再点取消；已签约不可勾流失（作废走财务流程）；「接洽中」为起始态不可取消。
  **任何改动停留清零、当天重新计时，提醒跟着重算**——点错造成的偶发不做特殊处理（用户定）
- 「停留」列 = 当前状态 pending 天数；**勾「已签约」→ 自动通知财务开 S1 定金 Invoice**（整条链第一条通知），其余勾不惊动别的部门

### 三个填写时点（严格分开）
1. **预测报价（范围，低–高）**：立项引导第 5 步填 —— 立项阶段没有真报价，无版本概念（quote_version 废弃）
2. **报价单号 / 预测人工工时 / 签约定价**：三样在「**待签约**」阶段一并填（预测工时=人工消耗率分母）
3. **定金**：只读列，财务写入后亮绿

### 立项与子表
- **立项完成 = 真建档**（十五轮定，用户实测发现原型只走过场后改）：第 5 步「完成立项」即刻在大表顶部插入新行
  （编号自动取现有最大 +1、状态=接洽中、立项时间=当天），扇形/当月新立项柱同步 +1；正式系统对应写 `project` 表
- **立项 = 大表上的按钮 → 5 步引导**：①基本与地址 ②联系人（每人五项：姓名/昵称/电话/邮箱/角色）与佣金（**佣金永远跟关系人同组**）③家庭成员+参建方 ④房屋（9 选）/施工阶段（含地下室、其他+说明）/楼层×5+屋顶/免责维保 ⑤方案倾向（有无 KNX/地暖）+预测报价范围
- **子表走行内「补全」抽屉**：大表只显示个数角标（参建方 2 · 成员 4 · 方案✓ · 楼层✓），**未填标黄**；
  参建方与方案倾向是**下游硬依赖**（出库提货人/Builder 告知/SM 电工签字/SM2 带线清单）
- **子表内容在大表直读**（2026-07-30 八轮补）：参建方（工种·联系人）→「联系人+参建方」列组末列；
  楼层·屋顶 →「房屋+楼层」列组末列；家庭成员 → 独立列组「成员构成」——格子里「改」进补全抽屉，未填标黄
- **下拉选项不写死**：联系人/关系人**角色**与参建方**工种**的选项列表由售前「设置 → 下拉选项管理」维护，
  加删即时生效（大表与立项引导同步启用）；删除选项不影响已填过它的历史数据 —— 落库对应两个配置键（v0_32）
- **双注释**：行尾财务注释+工程注释（列组里），售前填 → 对应部门必读（已读✓/未读 角标）；
  **多行大框**（小字 textarea，可拖右下角加高），**鼠标悬停弹浮窗显示全文**（九轮定）
- **「修改」抽屉（原「补全」，九轮更名）**：里面**全部可编辑**——联系人五项每格输入框、
  家庭成员/参建方每行可删（红✕）可加行、方案倾向与楼层全下拉；三个联系人角色行固定（内容可改）。
  原则：**凡展示即可改、凡列表可增删**（只读必须显式说明原因，如定金=财务写）

### 项目收款 S1-S3（旗舰页，照 §14 大表模板）

- **门禁双向**：S2 按钮被 SM3 卡、S3 被 SM4 卡（disabled+悬停原句）；反向 S1 结清→工程可进场+售前定金亮绿、

### 尾款结算 S4 与 Variation
